# Notes — raw dump, 2026-09-12

Brief chosen: **1. Housing maintenance triage** (docs/task-briefs.md). Decided 2026-09-12
after weighing all six against the judging criteria; runner-up was 4 (inspection
prioritisation), whose feedback-loop trap we fold in as a measured extra.

Why 1 wins on the criteria, not on ease: NT-specific (judges are CDU + OpenAI), the
trust twist is measurable (town vs remote wait-time gap), synthetic data can be built to
contain the skew on purpose, and the demo is visual (map + two rankings + a slider).

## One decision, one user

- User: a housing maintenance coordinator, NT public housing, remote communities.
- Decision: **which jobs get the available trade crews today, in what order.**
- Not the decision: budgeting, contractor procurement, tenant eligibility. Out of scope.
- AI assists, human decides: the coordinator signs off the dispatch list. The signed list,
  the weight setting and the reason are logged. Nothing is dispatched by the system.

## What the coordinator sees (the prototype)

- Inbox of free-text fault reports (synthetic), e.g. "aircon dead 3 days, baby in the
  house", "back door lock broken", "toilet overflowing into yard".
- Each report parsed to a structured card: fault type, safety risk, household
  vulnerability, location, logistics (distance, road status, crew already nearby).
  Every extracted field shows the source phrase it came from.
- Ranked list with the score broken into factors, plus one plain-English "why it sits
  here" per job.
- **Two rankings side by side**: efficiency-only vs equity-visible. A slider between them.
  Live metrics: remote median wait, town median wait, the gap, total travel cost.
- Sign-off button: coordinator picks the setting, writes a reason, signs. Logged.
- **Tenant view**: enter a job id, get a plain-language answer incl. the counterfactual
  ("14th now; would be 3rd if distance were ignored; coordinator approved this setting
  because ...").
- **Feedback-loop simulation** page: run the system 90 days efficiency-only, watch remote
  reports dry up ("no demand there"), compare with the equity-visible setting.

## Calls already made

- LLM does extraction from free text and drafts explanations. LLM does **not** rank.
  Ranking is a transparent weighted score so the factors are honest, not post-hoc.
- Ranking = urgency + safety + household vulnerability + logistics, with an explicit
  equity term the coordinator controls. Exact form decided in the PRD/architecture.
- Data is synthetic, generated by us, with the town/remote skew built in deliberately and
  documented. Geography (community locations, distances, wet-season road closures) comes
  from public NT sources where we can find them.
- Python. Interactive prototype likely Streamlit (fast, judges can run it). Confirm in
  create-architecture.
- Shares the remote-NT geography layer with the Data Innovation Challenge entry.
- Not in v1: real tenant data, real work orders, mobile app, multi-language UI,
  scheduling/route optimisation for crews (we rank, we do not route).

## Research needed (for the `research` skill — dated sources, into docs/)

Datasets is a judging criterion; every source below goes into the report.

1. NT remote community locations and populations: is there an open dataset (NT Govt
   open data portal, ABS, Bushtel)? Licence?
2. Road network / wet-season closures: NT road report, any historical closure data.
   Distances Darwin/Katherine/Alice to communities.
3. NT public housing: remote housing maintenance program facts (number of dwellings,
   published response-time targets for urgent vs routine repairs, any audit/ombudsman
   report on remote repair delays). These justify the synthetic data's shape.
4. Fault categories and urgency classes used by real housing maintenance (NT or other
   Australian states) so the synthetic taxonomy is credible.
5. Prior art: multi-objective / fairness-aware prioritisation with human-set weights;
   counterfactual explanations for rankings; feedback-loop (runaway) effects in
   predictive allocation (predictive-policing literature is the known reference).
6. Judges: Cat Kutay's research focus (community tech, Indigenous knowledge); what an
   OpenAI judge will probe (evals, human oversight).
7. Stack versions: Python, Anthropic SDK (which model, cost per report), Streamlit,
   pandas, any map library. Read versions from the lockfile, not memory.
8. Cultural safety: how to talk about remote Aboriginal communities in the report and UI
   without stereotyping; whether to name real communities or use synthetic names.
